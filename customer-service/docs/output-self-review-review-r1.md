## 0. 结论

- **verdict = needs_revision**
- 一句话：该需求以「用确定性校验拦住坏内容」为目标是对的，但**按当前取向实现将搭建第二套渲染/状态机**（服务端二判围栏、前端按裁决重渲染、渲染后回传重写），成本与回归风险远超收益；而实测证明**用户被冒犯的根因是「展示决策没有单一可信裁决者」**，可以用更小的改动消灭。需求必须先修订「方案取向」与验收判据，再进入实现。

## 1. 判据源头：用户原话

> 「客服输出的内容，比如渲染的图的内容，你应该先内部校验一下出的图是否通过才能输出，不通过需要修改，也就是需要有一个输出前的进行自我审核机制，避免错误的内容也直接输出给用户查看了，那是不对的。」

拆成三条可验收语义：

| # | 用户语义 | 本文纪律 |
|---|---|---|
| U1 | **先校验再输出**：图没通过校验，就不能出现在访客眼前 | 用实测证据判定"是否真的先校验" |
| U2 | **不通过要修改**：拦截后要有纠正动作，而不是丢掉不管 | 缺失纠正动作必须显式标为未满足 |
| U3 | **错误内容不得被访客看到**：任何路径下都不例外 | 逐条实测"访客最终看到什么" |

## 2. 现状实测证据（全部在本机真机工况下跑出，命令与原始输出见第 7 节）

### E1 — 目前**不存在**任何输出前校验：校验发生在访客设备上、渲染时刻、渲染失败之后

`grep -rn "validate|校验|gate" customer-service/plugins/*/src/*.ts customer-service/web/guest/index.html` → 无一条校验逻辑。
唯一的"把关"是访客浏览器里的 mermaid 渲染失败分支（`index.html:1078-1081`）：只 `console.warn`，**保留代码块**。

```
// customer-service/web/guest/index.html:1078-1081
} catch (err) {
  // 语法错误 / 渲染异常：保留原始代码块，控制台留证据
  console.warn('[guest] mermaid 渲染失败，保留代码块：', err && err.message)
}
```

→ 这是**事后兜底**，不是"输出前自审"；对用户 U1/U3 均为不满足。

### E2 — 访客真的会被送达**未经任何校验**的图形块（拿真实线上回答取证）

对运行中的访客出口 `POST /api/guest/chat/stream` 提问「遇到停电怎么办？」「如何缴交电费？」（均为欢迎页建议问题），实测返回：

- `done.reply` 内含 ` ```mermaid … ``` `（mindmap / flowchart TD）与 ` ```html … ``` `；
- **该轮回答由 924 个 `delta` 帧逐字送出**：visitor 屏幕上看到的是**流式累计文本**在数秒内逐步成型（`index.html:1567-1574`，每个 delta 都重跑 `renderMarkdown(streamed)` 并整体替换 `bubble.innerHTML`）；`done` 帧（`index.html:1577-1592`）只在该轮**收尾时**把 `streamed` 换成权威 `data.reply` 再渲染一次；
- 关键实测：**第 38 个 delta 时访客 DOM 里已经出现原始围栏分隔符 ```**；**第 70 个 delta 时，累计文本里已出现完整的 ```mermaid 源码块**——此时距 `done` 帧还有数百帧、数秒之久。

> 结论方向：把校验放在 `done` 时刻（现状语义）**从原理上无法阻止中途暴露**——内容早已上屏；这也正是 F2/F3 要求先冻结"块级缓冲"与"重写作用域"的原因。

把页面 `index.html` 的真实解析函数（`esc/inlineMd/renderMarkdown/imageSrcOf/renderImageBlock/renderMermaidBlock`，逐字截取、未改写）在 Node 中回放，喂入上述真实泄漏样本，得到**访客此刻 DOM 的实际 HTML**：

```html
<div class="mermaid-src" data-src="mindmap
  root((缴交电费))
    电子支付
    自动转账
    网上银行"><pre><code>mindmap
  root((缴交电费))
    电子支付
    自动转账
    网上银行</code></pre></div>
```

→ **原始围栏源码实时出现在访客眼前**（"流式期间只当代码块"，代码块 = 明文源码）。这是当前 100% 可复现的线上行为，也正是用户抱怨的"错误的内容直接输出给用户查看"。

### E3 — 渲染失败后，原始源码**永久**留在访客眼前

同一回放，喂入非法 mermaid（`flowchart TD\n  A[X --> B[Y]`，经 jsdom + 与访客同版本的 `mermaid-11.16.0.min.js` 实测 `parse` 抛 `Parse error on line 2`、`render` 亦失败）：

- 失败分支不改 DOM（见 E1 代码）→ 访客看到的就是 `<div class="mermaid-src">` 里的 `<pre><code>flowchart TD&#10;  A[X --> B[Y]</code></pre>`；
- 与 mermaid 官方默认行为一致：解析错误时在容器内**持久渲染错误图**（mermaid 11 默认 `suppressErrorRendering` 未开）——即"坏图 + 原始源码"双份暴露。

→ 用户 U3 在**当前代码里就是被违反的**，且失败后没有任何纠正动作（U2 不满足）。

### E4 — 图片栅栏未经校验就发起真实请求；目录穿越路径可回落到 API 出口

- `renderImageBlock(body)` 直接产出 `<img src="/uploads/not_exist_abc.png" …>`（回放实证），404 后才由 `chatEl` 的 `error` 委托降级成文字（`index.html:1313-1321`）——仍是**事后**兜底，且已向不存在的地址发出请求。
- `imageSrcOf` 对非自家路径原样放行：`/uploads/../../api/guest/health` → `/uploads/../../api/guest/health`；`curl --path-as-is` 实测**返回 200 与 guest health 的 JSON**（ngrok/nginx 归一化后回落到 `/api/guest/`）。即"图片地址"可被用来探访客 API 表面。

### E5 — 坏内容**没有任何留痕**

全仓检索无渲染失败/坏块的上报通道：前端只有 `console.warn`（访客控制台，团队看不到），`guest-server` 无任何被拦内容日志。→ 团队无法发现"模型反复出错"，与用户诉求中的运营价值缺失。

### E6 — 文案基础已具备（但缺"降级/校验不通过"专门文案）

i18n 字典（`index.html:254-355`，zh/zhHant/en/pt）已有 `imageUnavailable`（图片不可用，4 语言齐备），但**没有**"图表无法显示/内容已隐藏"这类降级文案，也没有任何"校验不通过"的用户可见表达。→ 新增文案必须进字典，这条要求合理且必须保留。

## 3. 核心评审意见：方案取向会让改动变大、正确性变差

需求取向要求：服务端**再解析一遍**围栏（mermaid 语法 parse + 图片可达性 + chart JSON 合法性 + html 块静态检查）→ 下发逐块裁决 → 前端按裁决渲染/降级/丢弃 → 渲染后再实测回传 → 触发重写。

按此实现会产生三处**新的、结构性的**不满足：

### F1 — 同一内容存在两套解析事实源，必然口径漂移（P0，必须修正需求）

服务端与访客端是**两套解析器**：服务端用 jsdom + mermaid parse（只有语法结论），访客端用真浏览器 render（只有几何结论）。二者结论不可能一致：

- 合法语法 + 真机渲染异常（字体/尺寸/浏览器差异）→ 服务端放行、真机出坏图；
- 服务端 jsdom 下的**误判**：本次实测确认 `mermaid.parse` 结论依赖宿主全局（缺 `structuredClone` 时 4 类图中 2 类样例直接抛错）——这正是"确定性校验"最脆弱的地方；
- 误判任一方向都是事故：**误拒**=访客看不到本该正常的内容（比现状更差），**漏放**=坏内容照旧送达。

要求：需求必须写明"**单一事实源**"原则——**图形块能否显示的裁决权归真机渲染器**，服务端只允许做**不依赖渲染**的检查（见 §4），二者重复的部分必须删除。

### F2 — `done` 重写与打字机流式互相打架（P0，必须修正需求）

实测（E2）：回答由 924 个 delta 逐字上屏，`done` 只是最后一帧。因此：

- "文字保持流式" 与 "坏块先校验通过才渲染、不通过重写整条回答" **不能同时成立**——要重写就必须把已经上屏的整段回答换掉，这是对用户的**内容突变**（已读到一半的内容被改写）；
- 现状 `done` 处理已经把 `streamed` 覆盖成 `data.reply`，若再叠加"服务端重写后的 reply"，会产生"上屏文本 ≠ 服务端最终事实"的时序竞争。

要求：需求必须明确 **重写的作用域与可见性**：是本轮**后续**内容（尚未上屏部分）还是**已上屏**内容？若前者，需定义"块级缓冲"边界（见 F3）；若后者，必须放弃"文字保持流式"这一条验收标准。

### F3 — "块级先审后渲染"缺少最小设计：围栏块必须单独缓冲

需求写了"分级门禁"却未定义**缓冲与放行协议**。当前失败模式的本质是：**围栏是否合法只能在它闭合之后才知道，而流式期间它已经在屏幕上以源码形式长出来了**（E2 实证：第 38 个 delta 起就开始长）。

要求：需求必须冻结一条**块级缓冲协议**（示例，供需求采纳或替换）：

1. 围栏起始（``` 行）→ 停止把该块内容上屏，改为"该块正在准备图形…"占位（文案进 i18n）；
2. 围栏闭合 → **真机**校验（mermaid parse/render、图片 HEAD 或预加载、chart JSON 解析、html 静态检查）与渲染；
3. 通过 → 用渲染结果替换占位；不通过 → 一次性替换为可读文字（含礼貌说明）；
4. 超时（给出预算值）或流中止 → 按"不通过"处理；
5. **任何分支都不出现原始围栏源码**。

这条协议才是**真的"块级先审后渲染"**——而且它**不需要服务端复算**就能成立，也不需要回传重写。

### F4 — "渲染后实测回传 → 触发重写"缺乏可行性论证（P1）

- 真机几何结论（空图/零尺寸/越界/异常比例）确实是现有服务端校验拿不到的**独有信号**，值得要；
- 但"回传即重写"会把"渲染失败"升级为"新一轮模型生成"：访客等待时间成倍增长，且**不能修正已经上屏的内容**；
- 未定义**重写预算**（次数、超时、失败后的终态）、**幂等**（重复回传）、**重入**（同一轮多处坏块）。

要求：回传的验收标准应降为"**留痕 + 降级**"（遥测可观测、访客看到可读替代），"触发重写"若要保留，必须补齐上述预算与终态定义，并证明其延迟影响。

### F5 — 遗漏了真正的根因：**可见性**没有被当作门禁对象（P1，用户 U1 的真正诉求）

用户说"避免错误的内容也直接输出给用户查看了"。现状的问题是：**没有任何环节决定"这块内容现在能不能显示"**。图片在 `image` 栅栏里**压根不走 DOM 沙箱**（它变成页面里的 `<img>`），因此"HTML iframe 已沙箱化"并不覆盖图片；mermaid 失败后源码留在屏幕上；块是否合法只在渲染失败后才被知道。

要求：需求必须增加一条**可见性门禁**验收标准：**任何图形块在被判定合格之前，其内容（含原始源码）不得进入访客 DOM**——这条是可执行、可对抗验证的（把 DOM 快照作为证据），比"服务端复算围栏"直接得多。

### F6 — 服务端 mermaid 校验的依赖与稳定性没有落到需求（P1）

补充 jsdom 的既有实测边界（供需求写"失败降级"时引用）：

- `mermaid.parse(合法源码)` 在 jsdom 下：flowchart / mindmap / sequenceDiagram / gantt / pie **均通过**；
- `mermaid.render()` 在 jsdom 下**必然失败**（`d.getBBox is not a function`）→ 服务端**不可能**做几何校验，几何只能来自真机回传；
- `parse` 结论受宿主全局影响（缺 `structuredClone` 时 pie 直接抛错）→ 服务端校验必须视为**概率性可用**，需求需明确"不可用时跳过该项、绝不让回答整体失败"的降级顺序。

## 4. 建议修订后的需求取向（供 `output-self-review-requirements.md` 采纳）

用"**单一裁决者 + 块级缓冲 + 只补真机独有信号**"替换"**双端复算 + 回传重写**"：

| 检查项 | 归属 | 理由 |
|---|---|---|
| mermaid 语法合法性与出图 | **真机渲染器**（访客浏览器，已有 3.5MB 库懒加载） | 现状已具备，且是唯一权威结论 |
| chart JSON 合法性 | **真机**（`renderChart` 已 `JSON.parse` + `Array.isArray`） | 已有，只需补"不通过时的可读降级" |
| html 块静态检查 | 可留在**真机**（`sandbox="allow-scripts"` + CSP nonce 已具备） | 已有安全边界，无需服务端复算 |
| 图片可达性 | **服务端或真机均要**（服务端 HEAD 更省访客流量） | 服务端拿到的是可达性，真机拿到的是"是否真的渲染出图"；两者互补 |
| 空图/零尺寸/越界/异常宽高比 | **只能真机** | 服务端 jsdom 拿不到 |
| 被拦内容留痕 | **服务端（主机侧）** | 团队可观测的唯一落点 |

对照用户三要素：

- **U1 先校验再输出** → 由「块级缓冲协议」满足：围栏闭合后先校验，通过才上屏。
- **U2 不通过要修改** → 先做**定向降级**（可读文字 / 礼帽文案），可选叠加"真机几何异常回传后，由主机侧决定是否重写**尚未送达**的后续块"——重写是增强项，不是唯一手段。
- **U3 错误内容不得被看到** → 由「可见性门禁」+「块级缓冲」满足：未判定的块不进 DOM；失败也绝不显示源码。

> 若「不通过必须由模型重写」是产品硬要求（而非我的推断），请在需求里显式写出**允许的最长等待增量**与**重写失败终态**，我会按该判据重新评审；否则建议按上表修订。
